# ljq 代码性能规范守卫

在每次修改前先识别数据规模、调用频率、事务边界和已有基础设施；修改过程中发现违反以下规则，立即指出并改成更小、更快、可验证的方案。不要为了“可能用得上”凭空引入中间件，也不要把性能口号当成实测结论。

## 实时纠偏流程

1. 先追踪完整调用链（入口、Service、远程 RPC、数据库、缓存或消息），找出循环内调用、重复查询、事务范围和热点路径。
2. 设计或改代码时同步检查本规范；发现风险时在当前回复中说明“风险 → 根因 → 最小修正”，然后继续实现，不等到提交前才提醒。
3. 修改完成后做一次针对性检查：SQL 形态、批次边界、并发/死锁、缓存一致性、消息幂等、索引命中和异常回退。能执行的就用 explain、日志、构建或最小可运行检查验证。
4. 若证据不足，标记为 `UNVERIFIED`，说明需要的指标或主人提供的环境信息；不要宣称已经获得性能提升。

## 数据库与 SQL

- SQL 以响应速度和可控锁范围为首要目标：能拆成更小的查询就拆，避免无谓的大表扫描、重复查询、隐式类型转换、无条件排序和超大事务。
- 禁止使用 `ON DUPLICATE KEY UPDATE`。需要写入或更新时，根据业务唯一键先分批查询，再分别执行明确的 insert/update；必须评估并发冲突、唯一约束和失败重试。
- 严格避免死锁：固定多表/多行访问顺序，缩短事务，按稳定主键顺序处理，避免在事务内调用远程服务或长时间等待；发现潜在锁环时先停下来修正。
- 新增字段、修改字段、增加索引或创建表时，必须把变更目的、字段/索引定义、兼容性、回滚方式和验证结果写入项目文档。若项目没有明确存储位置，先请主人提供文档地址；不得把 DDL 藏在代码注释或聊天记录里。
- Schema 文档与实际迁移必须保持一致；破坏性变更、锁表风险和线上执行窗口要明确标注。

## 批处理与循环调用

- 可以分批就分批。批量插入固定以每批最多 500 条为默认上限；批量更新、删除和远程请求也按数据量、SQL 包大小、超时和锁竞争选择合理批次，并处理最后不足一批的数据。
- 禁止高频 `for` 循环调用本地 Service。先判断数据规模和 Service 成本，优先改为批量接口、集合查询或一次性聚合；只有规模小且有证据表明成本可接受时才保留循环，并写明边界。
- 禁止高频 `for` 循环调用远程 Service 或 RPC。优先使用批量 RPC、并行且有上限的请求、消息异步化或本地缓存；必须考虑限流、超时、重试风暴、部分失败和幂等。
- 循环内不得重复构造相同参数、重复查相同数据或逐条开启事务；将可复用数据预取并按键组织。

## Redis、消息队列与 Elasticsearch

项目已有 Redis 时，优先评估热点读、短期结果、幂等键、分布式锁和限流是否适合缓存；明确过期时间、失效策略、穿透/击穿风险和一致性边界。不要缓存强实时且无法失效的数据。

项目已有消息队列时，能异步解耦的事件优先走 MQ，生产者与消费者必须定义幂等、重试、死信、顺序性和最终一致性；不要为了绕开一次简单同步调用而制造不可观测的异步链路。

项目已有 Elasticsearch 时，适合全文检索、复杂筛选或读多写少聚合的场景可使用 ES；明确索引映射、刷新策略、分页上限、数据同步来源和失败补偿。ES 不是事务数据库，最终一致性必须对业务可接受。

## 交付检查清单

- 是否存在循环内 Service/RPC 调用？给出调用次数上界和批量替代方案。
- SQL 是否可拆小、可命中索引、锁范围短？是否误用了 `ON DUPLICATE KEY UPDATE`？
- 批量写入是否按每批最多 500 条，并覆盖部分失败与重试？
- 是否在事务内做远程调用、发送 MQ 或执行慢查询？
- Redis、MQ、ES 是否基于现有设施和真实收益使用，并补齐一致性/幂等/失败策略？
- Schema 改动是否已写入指定文档；没有地址是否已向主人索取？

发现违规时，直接给出最小修复并在交付说明中列出未覆盖的性能验证项。不要新增单元测试框架；按项目约定做最小可运行验证即可。
