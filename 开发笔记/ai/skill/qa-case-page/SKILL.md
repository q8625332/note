# 测试用例页（qa-case-page）

一份需求的用例最终交付成**一个 HTML 文件**：离线可开、双击就能用、测试同学边测边点「通过 / 失败 / 阻塞」，最后一键导出 Markdown 存档。聊天里只回一段摘要和关键结论，不把整页用例贴成表格。

页面骨架、样式、交互都在模板里，已定型。你只负责写用例内容，套进模板的内嵌 JSON。

## 何时用

- 「按需求出测试用例」「写回归清单」「提测验收清单」「用例评审」
- 用户贴来一份现成用例页说「照这个风格写」
- 需求要分模块铺开、要区分「QA 能自己验」和「要开发先备数据」，或者有一堆产品还没定的点要单列

不要用：单条接口调试、单元测试、性能与安全专项（这些不在用例匠范围）。

## 交付物

1. 一个 HTML 文件，命名 `<需求名>-测试用例.html`。
2. 聊天里一段 5 行以内的摘要：验的是什么、几个模块几条用例、QA 可验几条、开发自验几条、待确认几条、最大风险是什么。

## 工作顺序

### 第 1 步：切模块

按**用户动作**切，不按代码模块切。好模块名是「建链接校验玩具归属」「玩具绑定账号上限」「账号封禁立即生效」；坏模块名是「Service 层改造」「接口 A」。

体量参考：一份中等需求 4～7 个模块、单模块 4～14 条用例、整页 40～60 条。少于 3 个模块说明拆得太粗，单模块超过 15 条说明该继续拆。每条模块都要写 `note`：这个模块改了什么、QA 该盯哪类结果，一段话，不复述用例。

### 第 2 步：一条一条写

固定三段式，字段含义与写法见 `references/case-data-schema.md`：

- 前置条件一句写完，最多带 3 个要素（谁、什么账号/设备、什么状态）。
- 步骤 2～6 步，一步一个动作，顺着真人从进页面到看到结果的顺序，不跳步、不倒序。
- 预期结果逐条对应步骤，写「页面出现什么、弹什么提示、列表多了什么、数量变成多少」。禁止「正常显示」「符合预期」「功能正常」「数据正确」。

一条用例只验一件事。要塞两个不相关的检查点时，拆成两条。

### 第 3 步：分验证方

- `qa`：测试同学用测试包、测试账号、常规设备就能独立跑完并判断对错。主流程、所见即所得的分支都放这里。
- `qa-dev`：验的还是用户看得到的效果，只是**测试数据造不出来**（如封禁中的账号、命中黑名单的设备、内部开白名单）。卡片必须在 `devAssist` 里写清要研发准备哪份数据。
- 数值阈值、日志、并发、历史数据、开关切换、构建产物这类 QA 看不到也判断不了对错的，**不要做成用例卡片**，写进 `devChecks`（开发自验清单）。这条边界是这份格式的骨架，别为了凑数把开发自验塞进卡片。

### 第 4 步：填页面其他四块

- `summary`：一段话说清改了什么、用户看到什么变化、QA 重点盯什么、哪些交给开发自验。
- `prep`：开测前必须到手的东西（环境、包、账号、设备、后台权限、开关取值）。没给齐不要开测。
- `devChecks`：开发自验清单，可以写到接口、日志、字段级，因为这不是用例卡片。
- `pending`：产品还没定、本轮不作为验收项的问题。每条点名影响哪条用例。

### 第 5 步：套模板

复制 `assets/case-page-template.html`，只替换 `<script id="case-data">` 里的 JSON，样式和交互一行不动。

写完必须做三件校验：

1. JSON 能解析（粘到任意 JSON 校验器跑一遍，或 `ConvertFrom-Json` / `JSON.parse`）。
2. 浏览器打开，页头事实栏、模块计数、卡片三段式、平台标记按钮都正常显示，控制台无报错。
3. 点几个「通过 / 失败」、改一次筛选、点一次「导出结果」，确认标记和导出正常工作。

模板已支持 `platformLabels` 自定义平台显示名；`slug` 决定浏览器本地标记的存储键，同一需求迭代时保持 `slug` 不变，历史标记才不会丢。

### 第 6 步：交付

`multica attachment upload <本地路径>` 把 HTML 交出去。运行环境的绝对路径不算交付物，别写进回复里当链接。

## 用例编号与命名

- 页面按模块自动编号 `1.1`、`2.3`（模块序号 + 模块内序号），不需要你手写编号。
- `key` 手写，全页唯一，用「模块缩写-动作」，如 `link-own-toy-ok`、`ban-kick-immediately`。key 稳定，改标题不要改 key，否则别人已存的执行标记会丢。
- 标题写成「动词 + 对象 + 结果」，如「用正确密码登录后进入首页」。
- `priority`：`高` / `中` / `低` 或省略。只有主流程、阻断性风险标 `高`，别整页都高。缺省不写就是普通优先级。

## 聊天里怎么回

页面交付之外，聊天里最多给 15 条表格速览（`| 用例编号 | 用例标题 | 前置条件 | 操作步骤 | 预期结果 | 优先级 |`），其余放页面里。超过 15 条时分批说明下一批验什么——页面是全量，聊天是速览。

表格后补两行：覆盖情况（正向 / 异常 / 边界各几条）、待确认问题（没有写「无」）。

## 审别人给的用例

用户只贴了一份用例没说审什么，默认按审用例处理。清单与输出三段格式见 `references/writing-rules.md`。对方交的是这份 HTML 页时，除了内容清单，再检查：有没有把开发自验塞进卡片、有没有 `pending` 混着验收项、每张卡片的验证方是否标对。

## 参考文件

- `references/case-data-schema.md`：`case-data` JSON 全部字段、取值、上下限、示例。
- `references/writing-rules.md`：写作铁律、反例→正例对照、审稿清单、覆盖度要求。
- `assets/case-page-template.html`：页面模板（含空白 JSON 与用法注释）。
- `assets/example-account-risk-502640.html`：真实交付样例（6 个模块 58 条用例 + 9 项开发自验），写之前先扫一眼它怎么切模块、怎么写预期。

## 不能碰的边界

- 不写自动化脚本、不写单元测试代码、不给接口调试建议、不做性能与安全专项方案。
- 用例正文不夹类名、方法名、SQL、接口路径、JSON、日志、报错堆栈、英文字段名。要指界面元素就用界面上的中文文案。（`devChecks` 是给开发的，可以写接口和字段。）
- 不虚构需求里没有的功能。需要业务规则判断时，先写 1～3 条假设，再往下写，假设写进 `pending` 让产品确认。
